# Preview 해석 입력 상한 분리 — 검토용 최소 변경

## 확인된 원인과 적용 범위

사용자가 제공한 Preview 진단은 `interpretation / INPUT_BYTES_EXCEEDED`이다.
`inputBytesWithOverhead=47336`, 기존 `maxInputTokens=16000`이며 모델명
`gpt-6.1-sol`과 최대 출력 25,000은 정책과 일치한다. 이는 공급자 요청 전에
발생한 입력 상한 거절이다.

새 서버 설정 이름은 `AI_INTERPRETATION_MAX_INPUT_BYTES`이다.
환경 파일이나 Vercel 설정에는 아직 추가하지 않았다.

| 상황 | 동작 |
| --- | --- |
| Preview + interpretation + 미설정 | 기존 Secret의 `maxInputTokens`를 그대로 사용. 현재 47,336 요청은 16,000 상한으로 계속 거절 |
| Preview + interpretation + `60000` | 이 요청에만 유효 상한 60,000 적용 |
| Preview + interpretation + 잘못된 값 | HTTP 503 `BUDGET_NOT_CONFIGURED`, DB 예약 및 모델 호출 전에 거절 |
| Q10 closing / legacy analyze | 새 설정을 읽지 않고 기존 정책 유지 |
| Production / 로컬 등 Preview 외 | 새 설정을 무시하고 기존 정책 유지 |

명시한 값은 공백·부호·지수·소수·선행 0 없는 정수 문자열이어야 하며,
4,096 이상 60,000 이하여야 한다. 빈 문자열도 잘못된 설정이다.
60,000은 자동 기본값이 아니라 명시적으로 설정할 때 허용하는 최대값이다.
기존 Secret·단가·필수 예산 설정이 없거나 잘못된 경우는 기존과 같이 거절한다.

## 검사·예약·정산의 일관성

`policy.ts`의 `featureBudgetConfig`는 기존 `budgetConfig`를 검증한 다음,
조건에 맞을 때만 **요청 전용 복사본**의 모델 입력 상한을 바꾼다.
기존 Secret, 단가, 공유 객체 및 다른 기능의 상한은 변경하지 않는다.

`reserveUsage`는 이 복사본을 한 번 확정한 뒤 기존 경로에 전달한다.

1. 모델 호출 전 비용 예약에 유효 입력 상한과 출력 25,000, 최대 2회를 사용한다.
2. 기존 사용자 월간 예산(계정별 설정 포함), 전역 일간/월간 예산, 이미 청구된
   금액 및 진행 중 예약액을 그대로 검사한다. 호출 횟수·동시성·중복 제한도 유지한다.
3. `price_snapshot.maxInputTokens`에는 동일한 유효 상한을 저장한다.
4. `ModelPermit.run`은 동일한 복사본으로
   `Buffer.byteLength(JSON.stringify(params), "utf8") + 4096`을 검사한다.
5. 보고된 실제 `prompt_tokens`도 같은 유효 상한으로 검증한다. 출력·캐시·추론
   토큰 검증은 유지한다. 알 수 없는/상한 밖 사용량이나 모호한 공급자 실패는
   기존처럼 전체 예약액을 보수적으로 유지한다.

요청 시작 후 환경 설정이 달라져도 해당 permit의 상한과 예약액은 바뀌지 않는다.
바이트 수를 실제 토큰 수로 단정하지 않는다. 기존 방식처럼 전체 SDK 파라미터의
UTF-8 바이트 수와 오버헤드를 보수적인 입력 토큰 상한으로 함께 사용한다.
프롬프트, 의미 데이터, 응답 계약, 모델/출력 설정, 인증 및 렌더링은 변경하지 않았다.

## 최대 예약 비용

입력 단가를 I, 출력 단가를 O (각 USD / 100만 토큰)라 하면:

```text
R = ceil(2 × (60,000 × I + 25,000 × O) / 1,000,000 × 10^8) / 10^8 USD
```

캐시 할인은 예약에 미리 적용하지 않으며 추론 토큰은 출력 25,000 안에 포함된다.
저장소 참고 단가와 합성 테스트의 I=2, O=10으로 계산하면 최대 예약은 **$0.74**다.
기존 16,000 기준은 **$0.564**로, 예시상 차이는 **$0.176**이다.
이는 공식 최신 요금 확인이나 실제 Secret 단가 확인 결과가 아니다.
실제 예약에는 기존 Secret의 단가를 사용하며 단가를 하드코딩해 바꾸지 않는다.

이 예시에서는 사용자 월간·전역 일간·전역 월간의 **남은 예산이 각각 최소
$0.74**여야 한다. 총 한도만 비교하지 않고 이전 사용액과 진행 중 예약을 포함한다.
남은 예산이 $0.60이면 기존 예약을 수용했더라도 새 예약은 `AI_BUDGET_LIMIT`로
거절해야 한다. 실제 운영 잔액은 조회하지 않았으므로 지금 실행 가능한지는 미확인이다.

## 검증 결과

- TypeScript: 통과 (`npx tsc --noEmit --incremental false`)
- ESLint: 통과 (`npm run lint`)
- 비DB 테스트: **534개 통과** (기존 478개 + 신규 56개).
  실제 배포 대상인 깨끗한 소스의 518개와, 별도 미커밋 인증 진단의 16개를 구분해 실행했다.
- 기존 PostgreSQL 보안 통합 테스트: **47개 모두 통과**. 운영 DB와 연결·볼륨을
  공유하지 않는 임시 로컬 PostgreSQL 16 컨테이너에서 실행했다.
  루프백 전용 동적 포트, 임의 테스트 암호, 임시 메모리 데이터만 사용했다.
  깨끗한 배포 소스에서 Preview 입력 상한 60,000을 활성화한 상태로 검사했다.
  운영 DB나 실제 OpenAI 키는 테스트 프로세스에 전달하지 않았다.
- `git diff --check`: 통과

신규 단위 테스트는 실제 정책/예약/permit/정산 코드를 메모리 DB 대역으로 실행한다.
47,336 바이트 요청의 기본 거절과 명시적 60,000 적용 후 허용, 정확한 경계,
설정 유효성·Preview 범위·기본 설정 유지, 두 번의 최대 호출과 세 번째 거절,
상한 스냅샷, 실제 사용량·불명확 실패 정산, 사용자/전역 예산 및 동시 예약,
기존 횟수·권한·중복·DB 실패 차단을 확인했다. 실제 API 보호 래퍼에서도
사용자 월간·전역 일간·전역 월간 예산 부족 시 HTTP 429 `AI_BUDGET_LIMIT`,
Retry-After와 no-store 응답 및 모델 호출 0회를 확인했다.
기존 통합 47개로 실제 PostgreSQL의 잠금·동시 프로세스·롤백도 검증했다.
기존 DB 잠금 구현은 변경하지 않았다.

## 배포 전 상태와 남은 위험

이 문서는 배포 전 검증 기록이다. 운영 DB·기존 Secret·예산 한도를 변경하지 않았고
실제 AI 호출도 하지 않았다. 기존 미커밋 인증 진단 작업은 배포 소스에서 제외했다.
검증 후 승인된 작업은 Preview에 새 입력 상한만 등록하고 새 커밋을 배포하는 범위다.
실제 Preview의 모델 응답 검증은 별도 허용된 실제 호출 전까지 미검증이다.

60,000은 현재 측정치보다 12,664바이트 여유가 있지만 모든 답변 조합과 재시도
추가 메시지가 항상 들어간다는 보장은 없다. 초과하면 계속 차단한다.
입력 토큰의 보수적인 상한으로 예약하므로 실제 사용량보다 큰 금액을 일시적으로
잡아 예산 부족이 발생할 수 있다. 이를 해결하려고 예산 제한을 자동으로 늘리지 않는다.
실제 모델 접근·완료 품질·지연 및 운영 DB 동작은 이번에 검증하지 않았다.
