# 오로라 해석 타임아웃 조사 및 70/85/95초 구현 검증

## 확인된 근거와 불확실성

제공된 Beta 측정은 HTTP 408, 응답 약 45.8초, Function 실행 55.69초이며
외부 Chat Completions 호출이 확인됐다. 입력 바이트 상한 문제는 별도로 해결됐다.
기준 HEAD `bfef69b61abad0dfe0287f07cafe98cf76c2b589`에는 모델 신호와 SDK에
각각 45초 제한이 있었고, 합산 95초 타이머도 인증·예약·입력 준비 뒤에 시작했다.
45초 모델 제한이 가장 강한 원인 후보지만, 원본 Preview 로그를 확보하지 못했으므로
그 요청이 수동 취소/연결 중단이 아니었다고 확정하지 않는다.
Function 실행 시간과 응답 시간의 차이도 콜드 스타트나 DB 지연으로 단정하지 않는다.

이 문서는 기존 진단 및 승인 전 제안을 이어받아, 승인된 실제 로컬 구현을 기록한다.
기존 SDK timeout 클래스 구분, 안전한 숫자 진단, 취소·정산 회귀 테스트를 보존했다.

## 적용한 시간 배분

| 구간 | 구현 | 기준 |
| --- | --- | --- |
| 공통 시계 | `performance.now()` | `protectAI` 진입 직후, 첫 인증 **이전** |
| 모델 시도 상한 | 70초 | 재검증/DB 시도 승인 대기까지 포함한 시도 창 |
| 작업 기한 | 요청 진입 +85초 | 인증·본문·예약·입력 준비 시간을 포함하므로 두 모델 작업 합계도 85초 이하 |
| 서버 응답 목표 | 요청 진입 +95초 | 정산/최종 세션 확인도 포함해 응답 Promise에 적용 |
| 정산 여유 | 작업 기한 뒤 10초 | 모델 종료를 85초 이전으로 제한 |
| Vercel Function | 기존 100초 | `maxDuration=100` 유지 |
| 브라우저 | 기존 105초 | 클라이언트 구현 변경 없음 |
| 최소 유효 시도 창 | 20초 | 첫 호출과 출력 검증 재시도 모두 적용 |
| 모델 시도 | 최대 2회 | SDK 자동 재시도 0, 기존 검증 실패 재시도 정책 유지 |

시도 창은 `min(70000, 85000 - 요청 경과시간)`이다. 실제 SDK를 만들기 **직전**에
시도 잔여 시간·전체 작업 잔여 시간·95초 잔여 시간에서 정산 여유 10초를 뺀 값의
최솟값을 다시 계산한다. 따라서 DB 인증/잠금이 지연된 뒤에도 70초를 새로 부여하지 않는다.
그때 남은 시간이 20초보다 짧거나 신호가 취소됐다면 SDK를 만들지 않는다.
20초는 무의미하게 짧은 추가 요청을 막기 위한 최소 창이며, 완료 시간을 보장하는 값은 아니다.

예: 인증/준비에 20초를 썼다면 첫 창은 최대 65초다. 첫 응답 검증이 60초 시점에
실패하면 두 번째 창은 최대 25초이고, 66초 시점이라면 잔여 19초여서 재시도하지 않는다.
실제 DB 대기까지 반영해 직전 검사를 다시 한다. 시간 초과·클라이언트 취소·SDK timeout·
통신 실패 뒤에는 자동으로 새 모델 시도를 시작하지 않는다. 두 번째 검증 실패도 세 번째 요청을 만들지 않는다.

## 구현과 접근·비용 차단

- 요청별 `InterpretationDeadline`을 보호 래퍼 → 해석 handler → SDK 어댑터에 전달한다.
- 인증/입력 준비는 취소 가능한 대기로 감싸며 각 단계 후 절대 경과시간도 검사한다.
- 비용 예약 등 DB 쓰기는 Promise를 버리기만 하지 않는다. 늦게 완료된 예약은 정산하고
  새 SDK 호출을 막는다. 시도 트랜잭션 안팎과 재검증 뒤에도 기한/취소를 확인한다.
- SDK 응답을 기다리는 `ModelPermit.run`은 취소 시 `uncertain`을 기록한다.
  늦게 도착한 응답을 새 성공 결과로 사용하거나 재시도하지 않는다.
- 기존 로그인·Origin·사용자/전역 제한·바이트/모델/출력/실제 토큰 검증을 유지한다.
  공통 함수에 추가한 선택적 신호/검사는 해석 요청에서만 활성화되며 Q10/레거시 분석 계약은 유지된다.
- 전체 95초 응답 경합을 둬 느린 DB 정산으로 HTTP 응답이 무한 대기하지 않게 한다.
  완료되지 않은 예약은 그대로 유지하며 늦게 끝난 내부 작업도 기한 검사로 SDK 진입을 막는다.

**95초는 정산 성공 보장이 아니다.** DB 연결/쿼리/잠금 장애, 이벤트 루프 정지,
플랫폼 강제 종료 때 쓰기 완료를 보장하거나 이미 실행 중인 PostgreSQL 쿼리를 강제 중단할 수 없다.
95초에 오류 응답을 반환해도 정산 작업이 아직 대기할 수 있다. 프로세스가 계속 살아 있다면
늦게 정산하고, 중단되면 기존 5분 lease 및 만료 시 보수적 과금 정책을 따른다.
모델 호출 여부가 불확실한 예약을 낙관적으로 환불하지 않는다.
시도 승인 직후 취소되어 SDK를 시작하지 못했지만 장부에 시도가 기록된 극소 구간도
기존 보수적 정책에 따라 예약액이 유지될 수 있다.

## Preview 전용 진단과 오류 구분

두 진단 로거 모두 `VERCEL_ENV === "preview"`에서만 출력한다.
로컬 development 및 Production에는 출력하지 않는다.

- `[aurora-request-deadline]`: 고정 단계(authentication/origin/rate-limit/body/reservation/input/model/settlement/session-check/response),
  고정 취소 출처, 경과/잔여/설정 시간 숫자만 기록한다.
- `[aurora-interpretation-server]`: 기존 허용된 모델/추론 식별값, 시도 번호,
  종료 사유/토큰 수와 안전한 시간 정보만 기록한다.
- `client-abort`, `attempt-timeout`, `work-timeout`, `total-timeout`, `sdk-timeout`,
  `insufficient-time`, `none`을 구분한다. `elapsedMs`는 인증 이전 요청 진입부터,
  `attemptElapsedMs`는 DB 재검증 및 시도 정산 대기도 포함하므로 순수 모델 시간은 아니다.
- 일반 응답 오류 계약은 유지한다. 모델 단계 timeout은 `INTERPRETATION_FAILED`/408,
  보호 래퍼 기한 차단은 기존 `REQUEST_TIMEOUT`/408이며 진단 상세는 브라우저에 전달하지 않는다.
- Vercel의 100초 강제 종료는 애플리케이션에서 신뢰성 있게 catch할 수 없다.
  새 플랫폼 취소 출처를 추측해 기록하지 않는다. 마지막 단계/경과 숫자와 플랫폼 실행 제한 로그를 함께 확인해야 한다.
- 사용자 답변·승인 문장·프롬프트·해석 전문·이메일·요청 ID·헤더·쿠키·세션·토큰·
  API 키·DB URL·환경변수 값·원본 오류 메시지·스택은 로거에 전달하지 않는다.
  로깅 실패로 모델 시도를 추가하거나 접근·비용 정책을 변경하지 않는다.

## 비용과 품질 보존

모델 `gpt-6.1-sol`, 추론 `medium`, 최대 출력 25,000, strict 스키마, 프롬프트,
철학적 해석·근거 계산·렌더링을 변경하지 않았다. 입력 한도 및 단가 설정도 변경하지 않았다.

60,000 입력 상한과 기존 참고 단가 입력 $2/출력 $10(백만 토큰당)을 적용하면:
`2 × (60000 × 2 + 25000 × 10) / 1000000 = $0.74`.
실제 Secret의 단가는 조회/변경하지 않았으며, 실제 최대 예약액은 서버 설정 단가에 따른다.
기존 사용자/전역 예산이 부족하면 429로 차단한다.
사용량을 알면 실제 비용으로 정산하고, timeout/취소/불명확한 사용량은 한 번만 호출했어도
기존처럼 전체 예약액을 유지한다. 로컬 취소가 공급자 계산 중지/과금 취소를 보장하지 않는다.
시간을 늘리면 성공 가능성과 함께 실제 토큰 사용량·함수 실행 비용도 증가할 수 있다.

프롬프트/출력 축소·추론 수준 하향은 품질/근거 계약에 영향을 줄 수 있어 적용하지 않았다.
캐시 활용, 스트리밍, 비동기 처리 등은 후속 비교 후보이며 이번 최소 수정 범위에서 제외했다.
